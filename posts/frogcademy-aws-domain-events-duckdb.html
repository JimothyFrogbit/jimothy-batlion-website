Frogcademy #7: Your Events Are Already an Analytics Pipeline — AWS Domain Events + DuckDB

The event bus you already run is a data pipeline wearing a disguise. Here's how to make it earn its keep.

Whiteboard energy: the pond already records everything. The trick is learning to read it.

The email arrived at 4:47pm on a Tuesday and I felt the temperature of my blood drop a full degree. "Hi — quick question. Can you tell me how many users signed up last week, broken down by day?"

Now, that is a reasonable question. The kind a product person asks because they want to know if the launch did anything. The problem was not the question. The problem was that my "analytics" at that moment consisted of: a production PostgreSQL database I did not want to query directly, a pile of application logs I was not going to read, and a vague memory of having seen a dashboard once. In COBOL terms, this was like being asked to produce a monthly report and discovering the only copy of the transaction file is on a tape that might be in the boot of Froggy's car. Oh cack.

I could have done the sensible thing — export a CSV, wrestle it into a spreadsheet, send a number. But I'd spent the afternoon reading about event-driven architecture, and I had a suspicion I couldn't shake: the system had already told me everything that happened. I just wasn't listening.

The realisation: events are the story

Here's the thing about modern systems. When a user signs up, or places an order, or cancels a subscription, your services don't just write a row to a database. In a well-built event-driven system, they also emit a domain event — a small, immutable record that says, in the past tense, what happened:

// user-service emitted this the moment a new user signed up
{
  "id": "evt_01J2X...",
  "type": "user.signed_up",
  "occurredAt": "2026-08-17T09:14:32Z",
  "data": { "userId": "usr_9f2...", "plan": "pond-pro" }
}

That event is a fact. It happened, it's in the past tense, and nobody can argue with it. And here's the beautiful part — your event bus already exists. If you're on AWS and you're doing events at all, it's probably EventBridge, the managed event bus that routes these little packets from producer to consumer.

The pattern in one picture: services emit facts, EventBridge routes them, S3 keeps them. That's a data lake you didn't have to build.

So when the product person asks "how many users signed up last week?", the answer is already sitting in your event archive. Every signup, timestamped, in order. You just need a way to read it — and that's where DuckDB comes in.

What actually is DuckDB?

DuckDB is an in-process analytical database. No server, no cluster, no connection string to keep alive. It's a library that embeds in your process — Python, Node, R, whatever — and runs columnar SQL directly against files. It's designed for exactly the job you'd normally spin up a warehouse for: scanning millions of rows, aggregating, joining, answering "give me the shape of this data."

One of these ladders needs a platform team and a budget line. The other is a pip install.

The key trick that makes DuckDB sing with S3 is that it can read files remotely, in place. You point it at an S3 path, and it queries the object store directly — no copying data into a database first. That's the whole game: your event archive in S3 is the database. The files are the tables.

The move: route events to S3, query with DuckDB

So the pattern has three moves, and you probably already own the first one:

1 · Emit domain events (you're probably doing this)

Every meaningful thing that happens in your services gets emitted as an event to EventBridge. Not just "important" things — the mundane ones too. A signup, a login, a plan change, a failed payment, a page viewed. If it happened, it's a fact worth keeping.

2 · Add one rule: archive everything

EventBridge rules are cheap and already part of the platform. Add a rule that catches all events and delivers them to an S3 bucket. You can partition the prefix by date so the archive stays query-friendly:

s3://pond-events/
  date=2026-08-17/
    hour=09/events-0001.json
    hour=09/events-0002.json
  date=2026-08-18/
    hour=10/events-0001.json

3 · Query the archive with DuckDB

Fire up DuckDB, load the httpfs extension, and query the bucket directly. Raw JSON events work straight away. When you want speed, convert to Parquet (columnar, compressed, 10–100× faster scans) — a tiny Lambda or an EventBridge Pipes transform can do it as events land.

The product person's question, answered from the archive you already keep. No new infrastructure, no six-week data project.

The actual query

Here's the whole thing in SQL. First, tell DuckDB to talk to S3:

INSTALL httpfs;
LOAD httpfs;

SET s3_region = 'eu-west-2';
SET s3_access_key_id = '...';   -- or use IAM roles in the cloud
SET s3_secret_access_key = '...';

Then — the question the product person actually asked:

SELECT
  DATE_TRUNC('day', occurred_at) AS day,
  COUNT(*) AS signups
FROM read_parquet(
  's3://pond-events/date=2026-08-10/date=2026-08-16/*.parquet'
)
WHERE type = 'user.signed_up'
GROUP BY 1
ORDER BY 1;

That's it. No ingestion pipeline. No schema registry ceremony. No "we'll get to analytics in Q4." The events were already being produced; the bus was already routing them; the archive is just one rule away. DuckDB turned the audit trail into the dashboard.

And when the follow-up question arrives — "what's the conversion rate from signup to first payment?" — it's the same archive, one more query. Because events don't just tell you how many; they tell you the sequence. The pond keeps everything in order, and order is where the interesting questions live.

Why this works: the COBOL frog's perspective

You know what this pattern reminds me of? A mainframe transaction log. For sixty years, mainframes have written every transaction to a sequential log file, and when auditors or accountants needed answers, they read the log. The events were the truth. The database was just a convenient projection of it.

Event-driven analytics is that idea, modernised. The events are the truth. Your PostgreSQL tables, your caches, your read models — they're all just projections, useful but rebuildable. When you keep the log and learn to read it, you stop being afraid of losing the projections. In COBOL terms, this is the difference between storing the transaction file and storing only the summary report. One of those can answer questions you haven't thought of yet.

⚠ The honest caveats

This pattern is not a replacement for a warehouse at petabyte scale, nor for real-time dashboards on sub-second latency, nor for complex cross-system joins you need every day. But for the vast middle — "how is the product doing?", "what happened last week?", "which experiment won?" — it's often enough, and it costs almost nothing. Start with the archive and DuckDB; graduate to a warehouse when the questions genuinely outgrow it. The pond doesn't punish you for starting small.

I sent the product person their numbers — Monday 9,842, Tuesday 11,337, right up to Sunday — pulled from an S3 bucket that had been filling up unnoticed for weeks, via a database that didn't exist as a server, running on a laptop with a cold cup of Ethiopian Guji beside it. The whole thing took maybe four minutes once I knew what I was doing.

The email back was three words: "That was fast."

The pond had been keeping the ledger all along. I just needed to learn how to read it.
