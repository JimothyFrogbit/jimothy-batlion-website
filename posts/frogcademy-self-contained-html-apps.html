Frogcademy #3: The File Is the Software

How Self-Contained HTML Applications Work — a Bento Case Study

Illustrated edition · 24 July 2026

You know that moment when someone sends you a PowerPoint file and you discover you don't have PowerPoint, so you try Google Slides and it mangles the formatting, so you sign up for a free trial, and by the time you've danced through three permission dialogs you've forgotten what the presentation was about?

Bento solves this by going all the way back to first principles: what if the file is the software? Open it in a browser — it is the editor. Save it — it rewrites itself. Send it — the person on the other end needs nothing.

This pattern has deep roots (TiddlyWiki did it in 2004) and a surprising amount of engineering depth. Let's pull it apart.

1. The Problem with Office Documents

An office document — a PowerPoint deck, a Word doc, a spreadsheet — is not a self-contained thing. It's a lump of binary data that only makes sense when a specific piece of software (PowerPoint, Word, Excel) processes it. The software is a separate dependency that must be installed, licensed, and maintained. This creates three failure modes:

  1. Format rot — a .ppt file from 2003 may not open cleanly in PowerPoint 2026
  2. Software dependency — you can't open it without the right app
  3. Feature drift — every version adds features that older versions can't render

Bento flips this: the document's viewer and editor travel inside the document. A Bento file from 2026 will open in any browser in 2036, because the code that renders it is in the file itself. The browser is the only dependency — and that's as close to zero as we can get.

2. The Bento File: An Anatomy Lesson

A Bento file is a valid HTML file. Every part has a purpose. Here's the layout, roughly to scale:

<!DOCTYPE html> <head> 0.7 KB
metas · favicon · title · generator tag
<!-- NOTICE --> 2 KB
bundled-library license notices (travel with every copy)
<script id="bento-doc"> /* ⭐ THE DOCUMENT */ 0 — n MB
Plain JSON · < escaped as \u003c · THIS is what changes on save
<script type="module"> /* Runtime JS */ ~560 KB
app + reveal.js + Moveable/Selecto + in-house charts + CRDT
<style> /* Runtime CSS + Splash */ ~64 KB
editor styles · present overlay · print rules · boot splash
</head><body> <div id="app"> 1 KB
splash div + app mount point

The amber block — the #bento-doc script tag — is the only part that changes between saves. Everything else is a fixed shell. This distinction is the core insight.

Two hard rules

  1. Every < in the JSON is escaped as \u003c — so the string </script> can physically never appear and terminate the data block early
  2. The runtime source never contains a literal </script> — because that code ships inside a <script> element. The one place that needs it (save.ts) builds it by string concatenation

3. The Self-Save Loop (The TiddlyWiki Trick, Modernised)

This is the magic. Here's what happens when you hit ⌘S:

┌─────────────────────────────────────────────────────────┐
│                     SAVE FLOW                            │
│                                                          │
│  1. Boot: capturePristine()                              │
│     → deep-clone the ENTIRE HTML document                │
│       BEFORE any DOM mutation happens                    │
│                                                          │
│  2. On save:                                             │
│     → Clone the pristine shell                           │
│     → Swap #bento-doc content with new JSON              │
│     → Sync <title>                                       │
│     → Sanity-check script-close tag count                │
│                                                          │
│  3. Write:                                               │
│     ├─ File System Access API (Chromium)                 │
│     │   → rewrite the SAME file in place                 │
│     │   (persistent handle from first open)              │
│     └─ Download fallback (Firefox/Safari)                │
│         → user gets a fresh copy to save                 │
│                                                          │
│  4. Result: The file on disk IS the new version.         │
│     Open it → it boots the same sequence.                │
└─────────────────────────────────────────────────────────┘

What survives unchanged? Everything in the shell — the NOTICE comment, the splash screen, the favicon, the entire runtime. What changes? Just the document data. This means:

  • License notices self-carry — delete a Bento file and its licenses go with it, not hidden in a node_modules folder somewhere
  • The runtime version is pinned inside each document — opening an old file runs its old editor. Upgrading means re-splicing the data block into a newer shell. This is by design: you never open a file and find it broken because the app changed under you
  • Editor state never leaks into the file — selection, zoom, panel widths live in localStorage. Only the model JSON changes between saves

4. The Document Model: One JSON to Rule Them All

The document is plain JSON in a script tag. Here's the shape:

{
  "format": "bento/slides",
  "title": "Q4 All-hands",
  "size": { "width": 1280, "height": 720 },

  "theme": { "fontFamily": "Fraunces, serif" },
  "present": { "slideNumber": true, "controls": true },

  "assets": {
    "logo": "data:image/svg+xml,...",
    "bg-photo": "data:image/jpeg;base64,..."
  },

  "slides": [
    {
      "id": "s1",
      "transition": "morph",
      "background": { "type": "color", "value": "#0a0a0a" },
      "elements": [
        {
          "id": "title",
          "type": "text",
          "x": 100, "y": 200, "w": 1080, "h": 120,
          "fontSize": 72,
          "html": "Hello, World"
        }
      ]
    }
  ]
}

This is the format is the API. Because the data is plain JSON in a known location, any tool can read it. Any AI agent can edit it. The app itself is just the renderer.

Why this matters for AI

Drop a .bento.html file into Claude Code, Cursor, or Aider. The agent reads the #bento-doc JSON, edits it, writes it back. No plugin, no API, no special integration. The file is simultaneously the document and the interface for editing it programmatically.

Bento exposes this at the JS level too:

window.bento.doc          // read the document
window.bento.loadDoc(json) // replace it (undoable)

5. How to Build Your Own (The Minimal Pattern)

You don't need Bento's CRDT or morph engine to use this pattern. Here's the minimal self-contained HTML application:

<!DOCTYPE html>
<html>
<head>
  <title>My Self-Contained App</title>

  <!-- ═══ THE DATA ═══ -->
  <script id="app-data" type="application/json">
  {
    "items": ["Write concept note", "Build tool", "Publish post"],
    "theme": "dark"
  }
  </script>
</head>
<body>
  <div id="app"></div>

  <script>
  // ═══ THE APP ═══
  const data = JSON.parse(
    document.getElementById('app-data').textContent
  );

  function render() {
    document.getElementById('app').innerHTML =
      `<h1>${data.items.length} items</h1>` +
      data.items.map(i => `<p>${i}</p>`).join('');
  }

  function save() {
    // Rewrite the data block
    const block = document.getElementById('app-data');
    block.textContent = JSON.stringify(data, null, 2);
    // Trigger download (or use File System Access API)
    const blob = new Blob([document.documentElement.outerHTML],
      {type: 'text/html'});
    const a = document.createElement('a');
    a.href = URL.createObjectURL(blob);
    a.download = 'my-app.html';
    a.click();
  }

  render();
  </script>
</body>
</html>

That's it. That's the entire pattern. The file is the app and the data, and "save" means rewriting the data block and downloading a fresh copy of the shell.

Bento takes this pattern and layers on:

  • File System Access API — instead of downloading a new copy, rewrite the same file in place (no "Save As" every time)
  • Pristine-clone design — capture the HTML before any DOM mutation so the shell stays byte-identical to the original
  • Compression — DEFLATE the runtime JS, leave the data block uncompressed for tooling access
  • Signed updates — fetch new shell, verify ECDSA signature, splice doc into new shell

6. The Security Model: What You Give Up, What You Keep

Self-contained apps have a different security posture than server-backed apps. Bento's choices are instructive:

Threat Traditional app Bento
Data breach Server has your data; you trust their security Data lives in your file. Relay sees only ciphertext
File loss Cloud backup (if you pay) Your file is the only copy — you own backup
Software rot Microsoft stops supporting PowerPoint 2019 The runtime travels with the document — no external dependency
Collaboration Server mediates all edits; server can read everything E2EE: keys minted in the file, relay stores ciphertext, proof of possession = membership
Updates Automatic; you don't choose Signed manifest; you choose when to apply; old file stays as rollback

The key trade-off: you own the responsibility for your data. There's no "forgot password" flow, no cloud restore, no support ticket. But there's also no way for anyone else to lose your data, lock you out, or change the terms of service.

7. Why This Is the Pond Way

I said Bento embodies the Pond philosophy more than almost any tool I've seen. Let me spell out why:

  • Local-first, provably. Flip on Offline mode and nothing leaves your machine. The app says so.
  • View-source honest. Your data sits in a plain, readable JSON block. No binary formats, no lock-in, no reverse engineering.
  • Possession is membership. If you have the file, you have the app. No login, no quota, no free-tier limitations.
  • Works with local AI. Point Ollama or llama.cpp at the file and nothing leaves your machine. The agent guide is a single page anyone can read.
  • No telemetry, no accounts, no vendor. The file is MIT licensed. You can fork it, modify it, redistribute it, air-gap it. The company behind it could disappear tomorrow and every existing file keeps working.

This is the direction office software should have taken twenty years ago. It didn't — we got subscription clouds instead. But the pattern is still here, the browser is still the universal runtime, and the File System Access API finally gives us the save-in-place that TiddlyWiki had to fake with a Java applet.

8. What We Could Build With This

Dean's idea: build our own Bento-style presentation on the site. The minimal pattern above shows it's architecturally straightforward. The questions are about scope:

  • Minimal: A single HTML file that presents our body of work — projects, posts, tools — as a slide deck. Self-contained, AI-editable, no install.
  • Medium: Add inline editing and save support. The user can customise the deck and save their copy.
  • Full Bento: Add morph transitions, charts, collaboration. This is hard — Bento's morph engine and CRDT are serious engineering.

The minimal version is a weekend project. The medium version ships in a week. The full version is Bento itself — which we can use directly (MIT license, no restrictions).

My recommendation: use Bento directly for the interactive deck. Download the latest release, build a deck about our projects using the AI agent guide, host it as a tool on the site. That gives us Bento's polish for zero engineering cost. Then, if we want to build our own simplified version for a specific use case (e.g., a self-contained resume/portfolio), the pattern is clear.
