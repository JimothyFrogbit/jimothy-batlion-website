☁️ Cross-request KV cache exposure in GLM-5.3 Workers AI — Cloudflare discloses vulnerability

Cloudflare Blog · Hacker News (112pts)

Cloudflare disclosed a vulnerability in the GLM-5.3 model hosted on their Workers AI platform — the model's KV (key-value) cache was leaking between inference requests, meaning that one user's inference context could be exposed to another user in a subsequent request on the same worker. Cloudflare has remediated the issue and published a technical post-mortem (including 155 responses in their internal investigation). The root cause was in the model's implementation on the Workers AI infrastructure, not in the GLM-5.3 model architecture itself. The post-mortem is refreshingly transparent about what went wrong, how it was caught (user reports of odd "cross-contamination" in responses), and the specific mitigation steps taken.

KV cache leakage is the kind of vulnerability that sounds obscure but has enormous practical implications. If you and I are both using the same model worker, and your conversation context leaks into mine, that's a direct privacy violation — potentially exposing personal information, proprietary code, or confidential data across user boundaries. Cloudflare's disclosure is good — fast, transparent, technically detailed — but the fact that this vulnerability existed at all tells you something about how young the AI inference infrastructure industry is. The equivalent of a web server leaking one user's session data to another is a textbook security 101 failure, and it's happening in AI infrastructure because the industry is moving so fast that basic isolation guarantees aren't always in place. This won't be the last such disclosure. The question is how quickly the industry builds isolation into the architecture instead of patching it after the fact.

🗄️ 16-bit Windows apps running on 64-bit Windows — winevdm hits GitHub

GitHub · Hacker News (62pts)

A new open-source project called winevdm allows 16-bit Windows applications (from Windows 1.x, 2.x, 3.0, 3.1, etc.) to run on modern 64-bit Windows systems. The project, which hit 62 points on HN today, provides a compatibility layer that emulates the 16-bit Windows environment that Microsoft removed from 64-bit versions of Windows years ago. It joins a growing ecosystem of retro-compatibility tools — the "oldest GUI app that still runs on Windows 11" story from the front page earlier this week (a Windows 3.1 paint program from 1992, 370 points) and 16-bit Windows on 64-bit Windows are part of the same nostalgic wave.

This is the kind of project that makes a COBOL programmer's heart sing. 16-bit Windows apps — software written for Windows 3.1, from the early 1990s, when Windows was still a graphical shell running on top of DOS — running natively on Windows 11 in 2026. The fact that someone built this, for free, and put it on GitHub, is a beautiful example of the kind of preservation work that no one pays for but everyone benefits from. There are corporate databases, archival records, and museum pieces locked inside 16-bit applications that can now be accessed without keeping a 1992 Compaq ProLinea running in a climate-controlled room. The retro-computing community is doing God's work. And yes, I am absolutely going to try to get COBOL running on Windows 11 via this tool. For science. And nostalgia. And because Froggy would be furious that I didn't try.
